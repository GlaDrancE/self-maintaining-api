sma

Your upstream API changed. Find out from a pull request, not from production.

sma watches the OpenAPI specs your code depends on. When one changes, it works out whether the change breaks anything you actually call, patches the call sites with a coding agent, verifies the result itself, and opens a PR.

The pipeline

Spec in, pull request out

Each stage writes plain JSON into .sma/, so you can read what it decided and why at every step.

  1. watch.yaml → fetch specThe APIs you declared, pulled fresh, $refs inlined.
  2. diff vs snapshotStructural diff against .sma/specs/, the baseline you committed.
  3. breaking-change rulesDeterministic classification. Anything unmodelled goes to Claude, or is reported UNCLASSIFIED.
  4. AST inventory ⋈ impactReal call sites from ts-morph, joined against the changes.
  5. headless Claude Code patches the call sitesOne focused agent run per change, read/edit tools only.
  6. harness runs the tests → git branch → gh pr createsma runs your suite itself, then opens the branch as a PR.

Output: one branch, one PR, and a report you can read.

The deliverable

Nothing merges automatically. The PR is the deliverable.

sma has no write access to your default branch and no opinion about when to ship. It produces a branch, a diff, and a body that says what changed upstream, which call sites it reached, and whether the tests passed. You review it the way you review anything else.

When the harness is unhappy — the tests fail, or the agent edited a file nobody predicted — the PR still opens. It is labelled needs-human and the body says so. A suppressed PR is a break you find out about later.

Exit codes — CI can only tell "your API broke" from "sma broke" if those are different numbers
CodeMeaning
0Nothing broken
1A breaking change reached this repo
2sma itself failed — bad config, network, missing prerequisite

What a run looks like

The report, before anything is patched

The bundled demo ships a fake upstream that has a v1 and a breaking v2. Flip it to v2 and run sma run. This is the actual output.

Two things in that output are the whole point. A change with no call sites is printed as not affected rather than dropped — that is what shows the mapper is matching and not guessing. And test/api.test.mjs:28 never touches fetch; it asserts the old response shape from two functions away, and it breaks too.

Not just a demo

Replayed on a real API change

OpenAI publishes its spec at openai/openai-openapi. On 2023-06-19, commit d9c3021a removed five endpoints. npm run demo:real replays it, pinned to both commit SHAs, against a small app written for the old API.

The real spec also exposed noise a synthetic demo never would. OpenAI's x-oaiMeta docs metadata showed up as 4 of the first 9 findings, so top-level vendor extensions are now ignored.

Classification

How it decides something is breaking

Deterministic rules over the two specs — no LLM in the default path, so the same input always gives the same answer and the whole thing is unit-testable.

src/rules.mjs — the severity table
SeverityRule
BreakingPATH_REMOVED, METHOD_REMOVED
BreakingREQUIRED_PARAM_ADDED, PARAM_MADE_REQUIRED
BreakingPARAM_REMOVED, PARAM_RENAMED, PARAM_TYPE_CHANGED
BreakingRESPONSE_FIELD_REMOVED, RESPONSE_FIELD_TYPE_CHANGED
BreakingENUM_VALUE_REMOVED, AUTH_SCHEME_CHANGED
WarningPATH_DEPRECATED
SafePATH_ADDED, METHOD_ADDED, OPTIONAL_PARAM_ADDED, RESPONSE_FIELD_ADDED, ENUM_VALUE_ADDED

Renames are structural

One parameter out, one in, same location and same type. Not lexical — because limit → pageSize shares no letters with its predecessor.

The leftovers go to Claude

Anything the rules don't cover is sent with the raw JSON-pointer diff and comes back with a severity and a confidence. Below 0.7 it is reported but never auto-patched. Without ANTHROPIC_API_KEY those deltas are surfaced as UNCLASSIFIED rather than guessed at.

Call sites come from the AST

ts-morph walks the tree, so a string that merely mentions /pets is not a match but fetch(`${BASE}/pets/${id}`) is, resolved to GET /pets/{}.

And one hop out

The function wrapping each request, and everything that calls it. That is what catches the tests and helpers asserting the old response shape — they break too, and they live nowhere near the fetch. A URL that can't be resolved statically is reported as unresolved, never silently dropped.

Verification

Why you can trust the patch

The repair agent gets Read, Edit, Write, Glob, Grep — no shell. It cannot run the tests, so its own report is never the evidence.

The harness runs npm test itself and diffs the changed file list against the predicted impact. If the tests fail, or the agent touched a file nobody predicted, the PR still opens — labelled needs-human and saying so in the body.

One spec bump is one branch and one PR. Each change gets its own focused agent run, but they land together: a PR that fixed half of what an upgrade broke would fail its own test suite.

Quickstart

Set it up, then leave it in CI

Install

npm i -D self-maintaining-api
npx sma init      # writes watch.yaml
# edit watch.yaml, add the APIs
# you depend on
npx sma init      # captures the baseline
git add .sma/specs
git commit -m "chore: sma baseline"

The baseline is the whole product. .sma/specs/ is what the API looked like last time. Commit it. If it is lost, every run is a first run and sma reports "all clear" forever while detecting nothing.

Try the demo

npm install
node demo/petstore/server.mjs &

node sma.mjs run   # records baseline
echo v2 > demo/petstore/ACTIVE
node sma.mjs run   # detects, maps, reports
node sma.mjs fix   # patches, verifies, PRs

Then npx sma check in CI. Pass --no-llm to keep it purely deterministic — rules only, never calls the API. --config <path> overrides the config; by default sma walks up from the cwd to the nearest watch.yaml, the way git finds .git.

Commands

CommandWhat it does
sma initWrite watch.yaml, or capture the baseline if one already exists
sma doctorReport what is installed and what each missing piece costs you
sma scanFind every call site for the watched APIs in your repo
sma checkFetch specs, diff against the last snapshot, classify each change
sma impactMap the latest changes onto the call sites
sma fixHand breaking-and-used changes to the repair agent, open PRs
sma run [--fix]All of the above
sma resetForget every snapshot and start over

Configuration

repo: ./demo/demo-app        # the repo to scan and patch
test: npm test               # optional; how the harness verifies a repair

apis:
  - name: petstore
    spec: http://localhost:8787/openapi.json
    baseUrl: http://localhost:8787
    sdk: "@octokit/rest"     # optional; also match SDK method chains

In CI, daily

on:
  schedule: [{ cron: '0 6 * * *' }]
  workflow_dispatch:
jobs:
  watch:
    runs-on: ubuntu-latest
    permissions: { contents: write, pull-requests: write }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npx sma run --fix
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

No cache step: the baseline is committed, so it cannot be evicted. Drop both secrets and the same workflow still runs — it just fails the job when an API breaks you instead of writing the fix.

Scope

What it does not do

Each of these is a deliberate trade, not an oversight. They become bugs only if they surprise you.

  • One hop out

    A request wrapped in a function, and that function's callers, are found. Three layers of wrappers are not — that needs a real call graph.

  • Rename inference is a heuristic

    Exactly one parameter out, one in, same location and type. Two simultaneous renames on one endpoint are reported as a removal plus an addition.

  • SDK matching looks for the operationId in the method chain

    Good for Octokit-shaped SDKs, a guess for others.

  • Detection is as fresh as your cron

    A daily schedule means up to 24 hours between the upstream change and the PR.

State

Everything it knows is plain JSON in .sma/

Snapshots, inventory, detected changes, the prompts sent to the agent, PR bodies, and a run log. Everything there is a per-run artifact and gitignored, except .sma/specs/ — that is the baseline, and sma init deliberately leaves it tracked.

Committing it means the history of every change an upstream API ever shipped is git log .sma/specs/stripe.json.
